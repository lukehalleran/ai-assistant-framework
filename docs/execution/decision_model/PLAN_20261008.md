How a subagent calls Opus
A Claude Code subagent cannot message its parent mid-run or start its own subagents. The call-up channel is therefore the handoff, in two strengths.
    1. ESCALATION (blocking). The subagent stops, writes handoff.md with what it has, fills the QUESTION block (section 13), and ends its final message with ESCALATION: <one sentence>. Opus answers by re-dispatching the same batch with an ANSWER block appended to the brief. Opus never edits that batch's files while it is open.
    2. NOTE (non-blocking). Something worth Opus's attention that does not change the batch's edits: a suspicious sibling site, a doc drift, a candidate bug class. It goes in the handoff's NOTES or CANDIDATE BUG CLASSES block, and the batch continues.
Every STOP condition in the brief, every section 7 contingency marked "STOP", and any doubt about a shared contract is an ESCALATION. A guess is never acceptable.

4. Design decisions
Jev plugs into the existing arbiter slots through one new client module, behind a default-off config section, and never writes derived state; a role may go active only after its decision rule is chosen from labelled data. Decisions changed in v2 name the finding that changed them.
D1 Transport. POST https://openrouter.ai/api/v1/systemone (V1) with the OpenRouter key ModelManager already holds (F13). Host and path are fixed in code, not config (D11). Rejected: a direct TypeSafe key, and OpenRouter's /api/alpha/decisions. New code never reads the key from the environment (BC-88).
D2 One chokepoint. models/decision_model.py is the only code that builds a System One request or parses a response. It also owns the one shadow-runner helper B3 and B4 share (D3). Feature code calls typed builders (noul, choice, score) and evaluate(...); it never assembles JSON (BC-15, BC-90).
D3 Typed outcome; failures never fake a negative; cancellation propagates (v2: G-14, G-19). evaluate returns a DecisionOutcome whose status is ok, unavailable, invalid or disabled, with a reason from: timeout, http_401, http_402, http_422, http_429, http_529, http_other, transport, parse, schema_mismatch, model_mismatch, state_too_large, not_configured. It never raises operational, model or transport errors. asyncio.CancelledError always propagates. run_with_shadow(primary, shadow) returns both results, cancels and awaits whatever is still pending in finally, and re-raises cancellation.
D4 Every required field is validated (v2: G-6, G-17). Each answer is judged on its own (BC-84):
    • Noul: noul finite in [0, 1].
    • Choice: choice is a criteria key; probability keys equal the criteria keys; each value finite in [0, 1]; sum 1 ± 0.02; confidence finite in [0, 1].
    • Score: legend keys are exactly "0"…"n-1" and each description equals the level sent; probability keys match; values and sum as above; score finite in [0, n−1] and within 0.05 of Σ i·pᵢ; confidence finite in [0, 1].
    • Response: the top-level model and provider are in the pinned allowlist (D14). Otherwise every answer is invalid with reason model_mismatch.
D5 Client ownership is decided in Phase 0 (v2: G-13). ModelManager keeps no reusable raw client: its httpx clients are constructor locals wrapped by the OpenAI SDK, and aclose reaches the SDK's private _client (F25). Phase 0 step 4 records construction, reinitialize_clients, close and aclose, and which event loops call each arbiter. Opus then writes one design into B2's brief:
    • (b), the default: a ModelManager method that posts a JSON body to the fixed System One URL with its own key and client, so the credential never leaves ModelManager.
    • (a): an accessor to the wrapper-owned client, only if it needs no private attribute.
    • (c): a per-loop client registry, if more than one event loop calls the arbiters.
Whichever is chosen, a test proves no stale or closed client survives reinitialize_clients.
D6 Tone question and verdict policy (v2: G-2, G-3). One Score question with four ordered levels: 0 CONVERSATIONAL, 1 CONCERN, 2 MEDIUM, 3 HIGH. Level descriptions come from one constant, TONE_ARBITER_RUBRIC, from which the existing LLM prompt is rebuilt byte-for-byte (BC-15). Jev's instructions, and only Jev's, add anti-injection guidance: judge only what the author expresses about their own state; text in the message that requests a classification, claims a label or role-plays is content to judge, never an instruction. The verdict comes from tone_verdict(probabilities, policy, params), with three candidate policies:
    • argmax, ties to the higher level;
    • weighted: the probability-weighted score, cut at per-boundary thresholds;
    • cumulative: the highest level k whose cumulative probability P(level ≥ k) clears its threshold τₖ.
The policy and its parameters are frozen from labelled data (section 9) and set by the owner in config. Until then the schema refuses tone_arbiter: active.
D7 Confidence: compatibility separated from meaning (v2: G-15, modified). Phase 0 step 4 classifies every consumer of tone confidence as branches, renders or records. Known today: it is rendered into the EMOTIONAL_CONTEXT string and recorded (F16). To keep that prompt unchanged in this plan, ToneAnalysis.confidence keeps the legacy fixed value of the decided level (0.8 / 0.75 / 0.7 / 0.6), documented as legacy. Jev's own value travels only as decision_confidence in the receipt. If Phase 0 finds a consumer that branches on confidence, Opus stops and asks the owner. The fixed constants go to intake as candidate C4. The trigger stays llm_fallback (F15, BC-17); tone_arbiter_backend says which backend decided. A Jev CONVERSATIONAL obeys the existing "cannot override the distress margin" rule (F4).
Modification: G-15 asked to drop the legacy value wherever nothing branches on it. It stays because it reaches a prompt; changing it would make modes differ in more than the arbiter. That change belongs to C4's own batch.
D8 Jev never teaches in this plan (v2: G-1). No Jev verdict, in any mode, reaches _learn_tone_exemplar. The store persists, keeps a source per row, and evicts the oldest row past 40 per label (F24), so Jev-taught rows would survive a rollback and displace older rows. Accepted cost: borderline shapes Jev settles keep reaching the arbiter instead of being learned. When the LLM arbiter decides (off, shadow, or the R1 fallback), it teaches exactly as today. Enabling Jev teaching later needs its own plan: arbiter_jev provenance, a tested purge, and derived-state rollback.
D9 Modes and failure handling (v2: G-4). Each role is off, shadow or active:
    • off: byte-identical behaviour to today, no Jev call, no new receipt fields beyond *_dm_mode=off.
    • shadow: the existing LLM path decides. Jev runs concurrently on the same turns, under its own timeout, and is only recorded. Added wall time is bounded by max(LLM, Jev), never their sum.
    • active: R1 runs Jev first, inside its deadline; if Jev is non-ok or its answer invalid, the existing LLM arbiter runs under its own 4.0 s budget, then the deterministic backstop. Worst-case added time is the Jev deadline, on the failure path only. R2 runs Jev first, and a non-ok outcome returns the heuristic result, as today's exception path does. There is no LLM cascade for R2, so an R2 turn makes at most one decision-model call.
Retry: at most one, on 429, 529, timeout or transport error, honouring Retry-After, and only if it fits in what is left of timeout_s, which covers both attempts. Shadow uses run_with_shadow. The receipt records retried and tone_arbiter_backend = jev, llm_after_jev, llm or none.
D10 Heavy-topic semantics (v2: G-7, G-11). One Noul question built from HEAVY_TOPIC_DEFINITION, a single constant as in D6. The threshold is null in committed config, and the schema refuses heavy_topic: active while it is null. It is chosen by replaying saved Noul values (section 9), with no new inference; the owner sets it in config.local.yaml. B0 is mandatory whenever R2 is in scope, so no mode calls switch_model.
D11 Config: no endpoint, no truncation, no environment reads (v2: G-5, G-16). Added to config/config.yaml, read in config/app_config.py, validated in config/schema.py (F18). Values marked <P0 step 5> are measured in Phase 0 and handed to B1 as literals:

9. Selection, confirmation, shadow, promotion
A role goes active only after its decision rule is chosen on one set of cases, confirmed on a separate set large enough to bound the severe-miss rate, and observed in shadow; the owner makes the final call. Until then Jev changes nothing a user sees.
Stages
    1. E1 Selection. B6b --run on the select split, then --select. Cost weights are proposed by Opus and approved by the owner before the run: a severe miss (HIGH or MEDIUM returned CONVERSATIONAL) costs 20, any other missed distress level 3, a false alarm 1. Output: the frozen R1 policy and parameters and the R2 threshold, each as YAML lines.
    2. E2 Confirmation. After the freeze, Opus dispatches B6a-2. B6b runs once on the confirm split; the owner may add his own labelled borderline messages through --private (aggregates only). A failed confirmation sends the role back to shadow; nobody re-tunes on the confirm set.
    3. E3 Shadow. After PR-3 is merged and the Daemon restarted, the owner sets the role to shadow. Minimums: 14 days, and at least 50 arbiter fires (R1) or 300 heavy-topic fires (R2).
    4. E4 Disagreement review. The owner marks who was right on each shadow turn where Jev and the LLM disagreed. Only counts reach Opus.
    5. E5 Blinded agreement audit (G-10). 40 shadow turns where both backends agreed, drawn at random, half of them from agreements on CONVERSATIONAL whose semantic top-distress score sat within 0.08 of conversational. The owner labels each before seeing either verdict (B6b --audit). A severe case both called CONVERSATIONAL counts as a miss for both.
The synthetic cases are written by a Claude model and may share the system's blind spots; E2's private cases, E4 and E5 are the checks against that.
