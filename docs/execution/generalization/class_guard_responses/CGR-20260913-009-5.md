`core/prompt/proposal_filter.py`'s `ProposalFilter.get_proposals` (def 610,
read-only per OWNERSHIP) calls `store.query_proposals(...)` at ≈661 with NO
surrounding try, so a `RetrievalError` propagates unchanged out of
`get_proposals`. `core/prompt/gatherer_knowledge.py`'s
`KnowledgeRetrievalMixin.get_proposed_features` (≈1118-1171, read-only per
OWNERSHIP) already does:
```python
proposals = await self._proposal_filter.get_proposals(query, limit=limit)
...
return proposals or []
except Exception as e:
    logger.warning(f"[ContextGatherer] Failed to get proposed features: {e}", exc_info=True)
    return OutcomeList.failed(type(e).__name__)
```
Before this batch, `query_proposals` swallowed every failure to `[]`, so
`store.query_proposals(...)` always returned an innocuous-looking empty list
and `if not proposals: ... return []` at the filter layer made a failed
store indistinguishable from "no proposals." Now that the store raises, the
raise reaches this method's own already-typed `except Exception` (its
`return proposals or []` line is never reached on a raise), which records
`OutcomeList.failed("RetrievalError")` — the filter and the gatherer needed
NO code change, the same "raise reaches an existing typed except" pattern
documented for F11a-1's thread reads.

Deployed-function test (through the REAL, deployed `ProposalFilter.get_proposals`,
bound to the REAL, deployed `KnowledgeRetrievalMixin.get_proposed_features`,
with only the innermost `ProposalStore.query_proposals` faked to raise — the

`CGR-20260913-009-4.md`'s coordinator test established):
