### `expand()` — explicit, uncached error (design-doc "never caches a failure")

Per `failure_outcome_design.md`'s CGR-009 decision ("expansion returns an
explicit error and never caches a failure") and its amendment "[map] The
expander caches its wrong error": before this batch, `expand()` had no
`try` around `result = self._do_expand(...)` at all, so ANY exception
(including the newly-raised `RetrievalError`) propagated raw out of
`expand()` — worse than the historical bug, which at least returned a
(wrong) dict; and a `_do_expand` result reached via the old swallow-to-`[]`
path was cached under `self._cache[cache_key]` exactly like a genuine
result, so a transient failure's wrong fallback text was served from cache
for up to `EXPANSION_CACHE_TTL_S` (300s) afterward.

After: `expand()` wraps ONLY the `_do_expand(...)` call in
`try/except RetrievalError as e:`, returning
`{anchor_id, collection, expansion_method="timestamp_window", turns=[],
total_in_collection=0, error=f"expansion_failed: {e.source}: {e.reason}"}`
and returning immediately — the `self._cache[cache_key] = (...)` line is
never reached on this path, so nothing is cached. Any other exception still
propagates unchanged (unaffected — `test_non_retrieval_error_from_store_propagates_out_of_expand`
proves a `ValueError` still escapes `expand()` via `pytest.raises`).
Deployed-function proof of the never-cache guarantee:
`test_range_producer_retrieval_error_not_cached` and
`test_anchor_get_by_id_retrieval_error_not_cached` each call `expand()`
twice with identical arguments and assert the store's call counter
increased on the second call (re-fetched, not served from `self._cache`).
Paired controls prove healthy/empty-but-genuine results ARE still cached
exactly as before: `test_control_genuine_empty_range_uses_fallback_and_is_cached`
and `test_control_healthy_expansion_is_cached` both assert `r1 is r2` on a
second `expand()` call.
