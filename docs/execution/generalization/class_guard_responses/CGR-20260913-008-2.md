## Upload-refusal defect (CM-07) — closed, with evidence

The request packet's "Observed shape and semantic risk" and the design
doc's "Real defects behind the scanner findings" both name the real-world
consequence of #103 as: *"A failed snapshot read during an upload's staged
replacement means old chunks are never replaced; stale and new versions are
both retrievable."* Before this batch, a failed/unavailable snapshot read
in `upload_document`/`upload_text` returned `[]` — structurally identical
to "no prior version exists" — so the upload proceeded, inserted the new
version, and never found (or attempted to delete) the stale old version.

Fixed: both methods now refuse before any chunking/embedding/insert/replace
when the snapshot read's status is `"failed"` or `"unavailable"`, appending
the constant `UPLOAD_REFUSAL_ERROR` and setting `result.success = False`.
Deployed-function evidence:

- `TestUploadRefusal::test_upload_text_refuses_on_failed_snapshot` and
  `::test_upload_document_refuses_on_failed_snapshot` (tmp_path file): a
  raising snapshot `.get()` → `result.success is False`, the constant error
  present in `result.errors`, and `mgr.chroma_store.add_batch_to_collection`
  / `mgr._replace_old_chunks` both asserted **never called** — proving
  nothing is inserted and nothing is deleted.
- `TestUploadRefusal::test_upload_text_refuses_on_unavailable_snapshot`: the
  same for a `None`/unavailable collection.
- **First-upload control**
  (`test_control_first_upload_on_empty_collection_succeeds`): a healthy,
  genuinely EMPTY collection (the `_collection()` cold-store/first-open
  semantics from the brief's parent-verified facts — a fresh
  `get_or_create`d collection returns `no_results`, never `failed`/
  `unavailable`) → `result.success is True`,
  `add_batch_to_collection.assert_called_once()`. This is the exact
  2026-08-02-incident shape (`tests/unit/test_refdocs_lazy_collection.py`)
  proven NOT to regress: a cold/first-open store still uploads normally.
- **Prior-version-replaced control**
  (`test_control_prior_version_is_replaced`): a healthy collection holding
  a real prior version (`succeeded` snapshot) → `result.success is True`,
  `mgr._replace_old_chunks.assert_called_once()` — the existing
  staged-replacement path is untouched.
- **`sync_file` (the 2026-08-02 duplicate class, defended one layer
  deeper)** (`TestSyncFileNoInsertOnFailedSnapshot`): a failing snapshot/
  hash read makes `_get_stored_content_hash` return `None` (unchanged
  behaviour — falsy `OutcomeList.failed(...)` short-circuits it), which
  falls through to `upload_document`, whose *own* snapshot read hits the
  same failing store and now refuses — `mgr.sync_file(...) == "failed"`,
  `add_batch_to_collection.assert_not_called()`. No insert happens at any
  layer.
- `tests/unit/test_sep09_storage_repairs.py::TestReplacementPreservesOriginal`
  (the F02 staged-replacement regression suite, real ephemeral ChromaDB, 5
  tests) stays **green, unmodified** — it never induces a snapshot-read
  failure (only `add_batch_to_collection` failures), so this batch's new
  refusal branch is never reached by that suite; its own defended behaviour
  (a mid-upload insert/embed failure preserves the original) is orthogonal
  and unaffected.

## Sibling determination (contract point 5 of the brief)

- **`chroma_store.query_collection` does NOT swallow its own failures**
  (`memory/storage/multi_collection_chroma_store.py:783-839`, read in
  full): no internal try/except; a raise from `_get_collection(...)` or the
  underlying `.query()` call propagates to the caller unchanged. This is
  why `get_documents`' semantic leg needed no local try of its own — a
  semantic-leg raise is already caught by `get_documents`' existing outer
  `except Exception`. (A different method on the same store, `search_all`,
  does wrap `query_collection` in its own try/except and return `[]` on
  failure — untouched, out of scope, not a sibling of anything this batch
  owns.) Recorded here for F9.
- **`get_full_document`** (511): a failed/unavailable read still returns
  `None` ("not found") — unchanged by design (brief contract point 5), not
  a candidate anchor.
- **`delete_document`** (857, now shifted): a failed/unavailable read
  returns `False` and logs "No document found" — misleading (a true read
  failure logs as a true absence) but safe, since nothing is ever deleted
  either way. Unchanged, not a candidate anchor.
- **`get_stats`** (886, now shifted): count 0 and an empty `documents` list
  on any failure in its own try (including a failed `list_documents()`
  call, since `len()` on an empty `OutcomeList` is 0 either way) —
  unchanged; an API-shape change here is explicitly out of scope per the
  brief.
- **Production consumers**, read-only per ownership:
  `core/prompt/gatherer_knowledge.py:741,897` (`get_documents`) and
  `core/agentic/tools.py:2034` (`list_document_titles`) both already treat
  their results as plain lists/iterables (`if not docs:`, list-comprehension
  filters, `for t in titles`) — behaviour unaffected by the `OutcomeList`
  wrapping, since it stays equal to `[]` and falsy when empty. F7 migrates
  them to read `.status`/`.reason`.
