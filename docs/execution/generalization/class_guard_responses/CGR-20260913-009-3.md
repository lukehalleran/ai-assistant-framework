## The pre-existing `get_summaries(limit=)` signature defect: NOT fixed (owner decision)

`_get_recent_summaries_by_timespan` calls `self.corpus_manager.get_summaries(limit=50)`
(unchanged, per the brief's explicit instruction). The production
`CorpusManager.get_summaries(self, count=5)` (`memory/corpus_manager.py:474`,
read-only in this batch) has no `limit` parameter, so on the real
`CorpusManager` this call has ALWAYS raised `TypeError` and has ALWAYS
returned `[]` -- narrative regeneration after consolidation has never
actually run. This batch does not fix the call (that is an owner design
decision per the brief); it only makes the failure visible instead of
silently swallowed. Pinned by `test_production_signature_raises_type_error_reason`,
which uses a fake `CorpusManager` with the exact production signature
(`get_summaries(self, count=5)`) and asserts the call now raises
`RetrievalError(source="corpus_summaries", reason="TypeError")` instead of

## The narrative consumer: explicit degrade

`_maybe_regenerate_narrative` (the only caller of
`_get_recent_summaries_by_timespan`, `memory/memory_storage.py` ~1563) used
to call the weekly and monthly reads directly; because both swallowed
their own failures into `[]`, a failed read and a genuinely empty corpus
were indistinguishable, and if ONE of the two reads failed while the OTHER
returned real rows, the method would still call
`generate_narrative_context` -- synthesizing a narrative from partially
missing input without any signal that anything was wrong.

Now: the two reads run inside `try: ... except RetrievalError as e: logger.warning(...); return`
-- a failure on EITHER read logs one warning ("Narrative synthesis skipped:
summaries unavailable: {e}", where `str(e)` is the leaf's label-only
"source: reason") and returns immediately, before even attempting the
other read or calling `generate_narrative_context`/`save_narrative_context`.
The best-effort `get_recent_memories` read (feeds the streak ledger) is
also no longer allowed to proceed silently on failure: its `except
Exception` handler now sets a local flag and logs a warning
("...recent memories unavailable: {type(e).__name__}"), and a check
immediately after the try/except returns early if that flag is set --
same outcome (log once, skip generation), restructured so the `return`
sits outside the broad `except` body (see Scan section below for why).
Genuinely empty summaries (both reads succeed and return `[]`) and a
missing consolidator still return quietly, as before; healthy reads still
generate and save.
