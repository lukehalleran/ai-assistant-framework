## The gatherer consumer: no code change, evidence only

`core/prompt/gatherer_knowledge.py`'s `KnowledgeRetrievalMixin.get_unresolved_threads`
(≈1278-1301, the only production caller of `MemoryCoordinator.get_unresolved_threads`,
read-only per OWNERSHIP) already does:
```python
threads = self.memory_coordinator.get_unresolved_threads(max_results=max_results)
return threads or []
except Exception as e:
    logger.warning(f"[ContextGatherer] Failed to get unresolved threads: {e}")
    return OutcomeList.failed(type(e).__name__)
```
Before this batch, the coordinator swallowed every failure to `[]`, so
`threads or []` always saw a healthy-looking empty list -- a failed read
was indistinguishable from "no unresolved threads" at the gatherer layer.
Now that the coordinator raises, the raise reaches this method's own
already-typed `except Exception` (its `return threads or []` line is never
reached on a raise), which records `OutcomeList.failed("RetrievalError")`
-- the gatherer needed NO code change; this is exactly the design note in
`failure_outcome_design.md`'s "F11a split": "A raise, by contrast, already
reaches its typed except, so the builder records failed."

Deployed-function test (through the REAL, deployed `KnowledgeRetrievalMixin.get_unresolved_threads`,
bound to the REAL, deployed `MemoryCoordinator.get_unresolved_threads`,
with only the innermost `thread_store.get_top_threads` faked to raise --
the same layered-fake pattern `test_gatherer_outcomes_remaining_knowledge.py`
established, but one layer deeper): `test_coordinator_raise_becomes_failed_outcome`
asserts `result == []` and `outcome_status(result) == ("failed",
"RetrievalError")`, with the injected marker absent from `result.reason`.

## The shutdown thread pass: the real-defect fix

`ShutdownProcessor._process_open_threads`'s open-threads read
(`memory/shutdown_processor.py` ≈1549-1558) previously caught the read
failure with a broad `except Exception as e: logger.warning(...)` and then
CONTINUED into resolution, extraction and storage with an empty
`existing_open` -- extraction ran with no "already tracked" list, de-dup
against existing threads saw nothing, and every extracted thread was
stored again as a duplicate (the `failure_outcome_design.md` real-defect
row: "an empty open-thread list (failed read) skips resolution and de-dup,
so duplicate threads are stored").

Now the except is narrowed to the TYPED `except RetrievalError as e:`
(never a broad `except Exception` -- see SCANNER SHAPE below), keeps its
warning log line, then adds `return` so the pass stops BEFORE resolution,
extraction and any store -- no duplicates. A short in-code comment
explains why. A genuinely empty open list (no exception) still runs the
pass exactly as today.

Deployed-function tests (`ShutdownProcessor` via `__new__`;
`THREAD_SURFACING_ENABLED` patched true; 2 session conversations;
`ThreadExtractor.extract_new_threads`/`detect_resolutions` monkeypatched
at the class level so any unexpected call raises `AssertionError`):
- `test_retrieval_error_skips_extraction_and_store_no_exception`:
  `thread_store.list_open_threads` raises `RetrievalError`. Asserts no
  exception escapes, `store_thread` and `enforce_cap` were never called,
  the extractor methods were never called (their `AssertionError`
  side-effects never fired), and the pre-existing warning log line still
  appears.
- `test_control_genuinely_empty_open_list_extracts_and_stores` (control):
  `list_open_threads` returns `[]` (no raise). Asserts extraction ran, both
  new threads were stored, and `enforce_cap` was called -- the pass
  behaves exactly as before for a genuine empty list.
