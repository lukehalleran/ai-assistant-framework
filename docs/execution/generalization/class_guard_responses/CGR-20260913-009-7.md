## Why a raise, not a typed `OutcomeList`

Both consumers already flatten a typed return value into a plain list
before it would reach a caller that could read `.status`:
- `core/prompt/gatherer_knowledge.py`'s `get_procedural_skills` (def
  ~1173) does `skills = await self.memory_coordinator.get_skills(...)`
  then `return skills or []` (line ~1210) — an `OutcomeList` returned from
  `get_skills` would be coerced to a bare `[]` by the `or []`, losing its
  `.status`/`.reason` before the gatherer's own
  `except Exception as e: ... return OutcomeList.failed(type(e).__name__)`
  ever got a chance to see it. A raise reaches that existing catch intact
  and is recorded as `("failed", "RetrievalError")` with no gatherer
  change required.
- `MemoryRetriever.get_reflections_hybrid` (def 849) calls
  `_metadata_fallback_search` with no surrounding try (line ~901) and
  merges its return value straight into a fresh `semantic` list — an
  `OutcomeList` return would be indistinguishable from a plain list one
  line later. A raise instead propagates to `get_reflections_hybrid`'s own
  callers, which already catch broadly.

This matches F11a-1/F11b-1's same design decision for other CGR-009
anchors (amendment "F12 split", `docs/execution/generalization/failure_outcome_design.md`).
