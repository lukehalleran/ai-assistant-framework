## Shutdown-time consumer: the write-loop count change

`ShutdownProcessor._process_open_threads`'s write loop (the only
production caller of `store_thread` for NEW threads, `memory/shutdown_processor.py`
~1608-1646) previously did `doc_id = self.thread_store.store_thread(thread);
if doc_id: stored += 1` with no try/except -- a raised `StoreWriteError`
would have propagated out of the whole method uncaught (the pass runs
inside `asyncio.gather(..., return_exceptions=True)` at its Phase-B call
site, so it would have been swallowed as one generic "generation"
LLM-failure log line for the WHOLE phase, silently dropping every
remaining new thread in the same batch and skipping Phase 3's
`enforce_cap`).

Now the call is wrapped: `except StoreWriteError: failed += 1; continue`
(a local `from utils.retrieval_outcome import StoreWriteError` sits right
before the try, mirroring F10b's identical pattern in
`_extract_procedural_skills`) -- the loop continues with the remaining new
threads, and Phase 3's `enforce_cap()` still runs afterward regardless.
The final log line changed from `if stored: logger.info(f"... {stored} new
thread(s)")` to `if stored or failed: logger.info(f"... {stored} new
thread(s), {failed} failed")` so a failure is visible even when nothing was
stored. A dedup/duplicate drop (no raise, no call) is still just "not
stored" and is never counted as `failed`.

Deployed-function tests (`ShutdownProcessor` built via `__new__` with only
`thread_store` and a stub `model_manager.generate_once`; `ThreadExtractor.extract_new_threads`/
`detect_resolutions` monkeypatched at the class level -- no real model
call):
- `test_one_write_failure_counted_second_still_stored`: two new threads,
  the first thread's `store_thread` raises `StoreWriteError`, the second
  returns a doc id. Asserts the method does NOT raise, both threads were
  attempted (`call_count == 2`), `enforce_cap` was still called, and the
  log reads "Stored 1 new thread(s), 1 failed".
- `test_control_genuinely_empty_open_list_extracts_and_stores` (control):
  both threads succeed. Asserts "Stored 2 new thread(s), 0 failed" and
  `enforce_cap` called.

## Delete-then-store siblings (F11a-2, not this response)

`ThreadStore.resolve_thread` and `_update_thread` (`memory/thread_store.py`
≈371-406, ≈461-489) both call `self.store_thread(thread)` without
capturing its return value, inside their own existing broad
`except Exception as e: logger.error(...); return False` -- unowned and
unchanged by this batch. Because `store_thread` now raises instead of
returning `None`, a failed re-store inside either method now correctly
surfaces as `False` (via their own existing except) instead of the prior
silent `True` after a successful delete-then-failed-store. This is an
externality of #146's fix flowing through unowned code, not a new edit,
and it does NOT close the "[verified] Delete-then-store loses the record"
defect: the delete still happens BEFORE the store is confirmed, so a
failed re-store still loses the prior document (no rollback). F11a-2 owns
reordering both methods to write-then-delete with rollback on a failed
delete, per `failure_outcome_design.md`'s "F11a split" amendment.
