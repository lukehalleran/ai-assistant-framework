## `_matches_phrase_non_negated` (line ~584) parity — BC-58

The rewritten line-~1178 check must agree with the sibling
`_matches_phrase_non_negated` (called at ~855) on negation for every phrase,
using the same `is_negated` lookback window. Verified two ways:

1. **By construction.** For every *phrase* entry in `EXPLICIT_SEARCH_PHRASES`
   (all but `'google'`), the new chokepoint's substring branch finds the
   first occurrence with `lower_text.find(kw)` — byte-identical to
   `_matches_phrase_non_negated`'s `text_lower.find(phrase)` — and both then
   call `is_negated`/`has_non_negated_hit` with the SAME default
   `window_tokens=5` (`DEFAULT_NEGATION_WINDOW_TOKENS`). No override is
   passed at either site. Text normalization is equivalent:
   `quick_prefilter_should_skip` uses `query.lower().strip()`,
   `_matches_phrase_non_negated` uses `_normalize(text) =
   text.strip().lower()` — same result.
2. **Deployed-function parity tests**
   (`test_bc58_parity_negated_phrase`, `test_bc58_parity_non_negated_phrase`)
   call both functions with the same phrase, negated the same way, and
   assert agreement: a phrase negated at ~855's site
   (`_matches_phrase_non_negated`) also counts as negated at the rewritten
   ~1178 site (`quick_prefilter_should_skip`), and a non-negated phrase
   counts as present at both. The negated-parity test failed pre-fix
   (`assert False is True` on the `quick_prefilter_should_skip` half) and
   passes post-fix; the non-negated half already agreed before and after.

**Divergence (expected, documented, not a defect):** the one bare word
`'google'` is now word-boundary matched at the rewritten ~1178 site but
remains raw-substring matched at the untouched ~584/~855 sibling — e.g.
"googlebot" no longer counts at ~1178 but would still raw-substring-match at
~584 if that site were exercised. This is the intended scope boundary: the
CGR's anchor #31 is the ~1178 call site only; ~584/~855 is reported as a
BC-58 sibling below, not changed.

## Trailing-comma markers (`"anyway,"`, `"by the way,"`)

Verified first, per the brief's contingency instruction. Both markers
contain a literal comma, so `compile_keyword_matcher`'s bare-word
classifier (`re.fullmatch(r"[a-z][a-z0-9_]*", stem)`) rejects them and they
fall through to the **raw-substring branch**, unchanged — the exact same
matching behavior the old code already had for these two markers. The comma
requirement is therefore already faithfully expressed through the
chokepoint with **no structural check needed** at this site, and no
vocabulary change. Confirmed behaviorally (not by reaching into matcher
internals):
`has_thread_break_marker("anyway, what about Python?") is True` and
`has_thread_break_marker("anyways what about Python?") is False` (the
comma-less near-miss does not fire), same for `"by the way,"`. Both pairs
pass identically before and after the edit — this was never a defect.
