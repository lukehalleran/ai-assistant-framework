## 2. Requirement / defect ID and invariant

- F03 / P1 parser defect; G12 strict boolean contract; probe Q13; bug
  classes BC-21 (compare/coerce on the serialized form), BC-50 (verifier's
  own false corrections — the class this defect can trigger), BC-63
  (validation must run through the deployed function, never a re-derivation).
- Invariant (parent contract, §5 of the task): a verdict is valid only when
  all five verifier-taught fields are present with their taught JSON type —
  `false_claim_present` a real Python `bool`, `confidence` a finite
  int/float (not bool) in `[0.0, 1.0]`, and `claim`/`why_false`/`correction`
  real `str` (not `None`). Any violation abstains (`None`), never coerces.
- Why the source seam owns the fix: `_parse_verdict` (core/grounding_check.py)
  is the single place that turns the verifier LLM's raw JSON text into a
  `GroundingVerdict`; it was calling `bool()`, `str(... or "")` and
  `float()` directly on untrusted model output, so a wrong-typed JSON string
  `"false"` silently became Python `True` (BC-21: coercing the serialized
  form rather than validating it).

### Decision: keep the strict contract and repair the fixtures

- The verifier prompt teaches all five fields (`core/grounding_check.py:279-283`, including `"why_false": one sentence ("" if none)`). A fixture without the field is drift from the taught schema (BC-64), not evidence of a looser contract.

- Watch item (owner canary, not a code change): if a live verifier model omits taught fields, `invalid_verdict` will show up in turn receipts. That rate is the signal for revisiting the contract.
