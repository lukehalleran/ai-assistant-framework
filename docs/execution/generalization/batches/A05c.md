## 3. Pruned cells (explicit, with reasons)

- **"flagged + integrator timeout" merged into "flagged + integrator
  failure (returns None)".** Re-read `core/grounding_check.py:1281-1367`
  (`integrate_grounding_correction`): its own `except asyncio.TimeoutError`
  (line 1322) and `except Exception` (line 1325) both `return None` — the
  function never raises to its caller for either cause. `_apply_grounding_check`
  (`gui/handlers.py:3352-3362`) treats a `None` return identically regardless
  of cause: falls to `build_integrated_fallback` with the same
  `grounding_status="fallback"` receipt. No caller — including this file's
  mocked seam (`grounding.integrate_grounding_correction` replaced wholesale
  by an `AsyncMock`) — can observe "timeout" and "failure" as different
  outcomes; the two matrix values collapse to one testable cell. Simulating
  "timeout" by having the mock *raise* `TimeoutError` would not be faithful
  to the deployed function's contract (it never raises) and would instead
  exercise a materially different, unrelated path — `_apply_grounding_check`'s
  own outer `except Exception` (line 3379), which reports
  `grounding_status="failed"` / `grounding_failure_reason="check_error"` and
  ships the draft unmodified. That path is already covered by the
  `verifier_failure` cell's externally-identical receipt shape, so nothing
  is lost.
- **log_only x verifier-outcome pruned to one control cell per route.**
  `_apply_grounding_check_for_delivery` (`gui/handlers.py:3093-3096`) returns
  `(None, "")` immediately in log_only mode, recording `ctx.grounding_pending`
  and `grounding_status="pending"`, without calling `verify_grounding`
  synchronously at all. There is no integrate-on/off or flagged/not-flagged
  branch reachable on the delivery path in this mode — only the
  already-existing "draft ships unchanged" behavior, tested once per route.
  (The verifier and integrator DO still run, in the background, after
  delivery — `_start_background_grounding`, `gui/handlers.py:3172-3210` —
  but that machinery and its status transitions
  (`pending`->`complete`/`timed_out`/`failed`/`cancelled`) are outside this
  batch's atomicity question and are already covered by
  `tests/unit/test_sep09_speed_batch.py` and `test_sep01_grounding_misfires.py`,
  per the draft's own note.)
- **log_only x cancel pruned entirely.** A05_design.md's invariant list
  assigns no delivery/cancel semantics to log_only, and this exact scenario
  (cancel while the background verifier is blocked) is already the subject
  of `test_grounding_cancel_storage_gate.py::test_log_only_cancel_keeps_storage_call`
  and `::test_log_only_agentic_cancel_keeps_storage_call` — re-proving it
  here would duplicate ownership rather than extend coverage.
- **Correct-mode cancel x verifier-outcome pruned to one blocking point per
  route** (8 cells collapsed to 2). Per the draft's explicit instruction.
  The cancellation in both cells lands inside `verify_grounding` before it
  returns, so which outcome it would eventually have produced cannot affect
  what already happened (no storage, one cancel receipt) — the outcome axis
  is moot once cancellation preempts it.

## 10. Limitations

- **Corpus/Chroma.** The design names "corpus/Chroma fakes" — the deepest
  seam available without constructing a live corpus/ChromaDB instance is
  `gui.handlers._dispatch_storage`, mocked with a `MagicMock` throughout
  (per the batch's HARD PROHIBITIONS). Every "stored text" assertion in this
  file reads `_dispatch_storage`'s call arguments (`call_args.args[2]`),
  never a real corpus or Chroma write path. This matches the fixture
  precedent in `test_grounding_buffered_delivery.py` and
  `test_grounding_cancel_storage_gate.py`.
- **Debug record vs. the SSE `complete.debug` payload.** `complete.data["debug"]`
  is PII-redacted before it reaches the client
  (`api/chat_service.py:137`, `redact_data(debug)`); this file compares
  against the server-held raw record (`state.session.debug_records[-1]`,
  `api/chat_service.py:127`) instead, per that file's own docstring ("the
  server-held record is kept raw").
- **"integrator timeout" is not independently exercised** — see §3's
  pruning rationale; the deployed `integrate_grounding_correction` makes it
  unobservable as a distinct outcome from "integrator failure" at any
  caller, including this seam.
- **Background log_only receipt-status transitions** (`pending` ->
  `complete`/`timed_out`/`failed`/`cancelled`) are not re-derived here; the
  log_only cells confirm the atomicity chain and the absence of a
  `delivery` key only, per the draft's own reference to the existing sep09
  coverage for those transitions.
- **No source file or existing test was read for correctness beyond what
  this file's own assertions needed** — `gui/handlers.py` was read
  (read-only) to confirm exact call-argument positions
  (`_dispatch_storage`'s `args[2]`), debug-record sync points, and the
  log_only short-circuit, but never edited.
