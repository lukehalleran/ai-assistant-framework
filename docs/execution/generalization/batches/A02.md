## Requirement and defect

F01 / G06-T02 / G06-A03 (client half). Before this batch, `web/src/api/
client.ts` and `web/src/api/useChatStream.ts` sent every `/api/*` request
(ordinary fetch, upload, action approval, SSE POST, session restore/clear,
prompt-export download) with **no `X-Daemon-Launch-Token` header at all**,
and the prompt-export button used a native `<a href="/api/debug/prompt?...">`
which cannot carry a custom header. Against A01's patched server, every one
of these calls would 401. This batch is the client half of that same F01/
G06-T02 authorization contract; A01 owns and already covers the server half.

## What changed

- **New `web/src/api/launchAuth.ts`** (104 lines). The single chokepoint:
  - `getLaunchToken()` reads `<meta name="daemon-launch-token" content="...">`
    lazily (module-memory cache; `undefined` = not yet read), matching A01's
    injection point (right after `<head>`). `__resetLaunchTokenForTests()`
    is the test-only reset hook the frozen contract asked for.
  - `authorizedFetch(input, init)` — wraps `fetch`, merging in the
    `X-Daemon-Launch-Token` header via a `Headers` instance built from
    `init.headers` (so `Content-Type` and other caller headers survive, and
    a `FormData` upload never gets a manually-set `Content-Type`). Missing
    token: the header is simply omitted (fail-closed via the server's own
    401, per the frozen contract — no invented token, no tokenless
    alternate path).
  - `authorizedHeaders(extra)` — same merge, returned as a plain
    `Record<string,string>` for `fetchEventSource`, which does not accept a
    `Headers` instance.
  - `downloadViaAuthorizedFetch(url, fallbackFilename)` — authorized fetch
    -> `Blob` -> object URL -> temporary, hidden `<a download>` -> click ->
    remove -> revoke. Filename from `Content-Disposition` (matches
    `api/routes/debug.py`'s `attachment; filename="..."` format) when
    present, else the fallback. Throws a **status-only** `Error` on failure
    (`Download failed (${status})`) — never the URL, body, or token.
- **`web/src/api/client.ts`**: every one of the 19 exported functions now
  calls `authorizedFetch` instead of bare `fetch`. `clearSession` (unused by
  any current consumer, confirmed by grep) now also throws on a non-ok
  response instead of silently resolving with it, for the same "401 must
  surface as an error" invariant the rest of the object already had via
  `json()`. `promptExportUrl` (a bare URL-string factory) is replaced by
  `downloadPromptExport(index)`, which calls
  `downloadViaAuthorizedFetch('/api/debug/prompt?index=${index}',
  'daemon_prompt_${index}.txt')`. Every other function name and signature is
  unchanged.
- **`web/src/api/useChatStream.ts`**: the mount-time `GET /api/session`
  restore and `clearAll`'s `DELETE /api/session` now go through
  `authorizedFetch` (they previously duplicated a raw `fetch` call rather
  than using `client.ts`'s `api.getSession`/`api.clearSession`; kept as
  direct `authorizedFetch` calls, preserving their existing bespoke
  ok/error-shape handling rather than folding into `client.ts`, per "prefer
  a design that does not require" touching `ActionApprovalCard.test.tsx` and
  to keep this batch's diff minimal). Mount restore additionally
  distinguishes a `401` (dispatches a visible `error` state) from a `404`/
  fresh-session non-ok response (silently treated as "no session yet", the
  pre-existing behavior) — so an authorization failure on refresh is no
  longer indistinguishable from a normal first launch. `send()`'s
  `fetchEventSource('/api/chat', ...)` call now passes
  `headers: authorizedHeaders({ 'Content-Type': 'application/json' })`.
  `abort()`/`AbortController` wiring, the `onerror` rethrow (no
  fetch-event-source auto-retry), and `openWhenHidden: true` are unchanged.
- **`web/src/components/debug/DebugPage.tsx`** (parent-approved amendment,
  only the "📥 Download full prompt as TXT" button, ~lines 319-333): the
  native `component="a" href={api.promptExportUrl(absIndex)}` is replaced by
  a plain `Button` whose `onClick` calls
  `api.downloadPromptExport(absIndex)` and shows a red `notifications.show`
  error (message only — status text from `downloadViaAuthorizedFetch`,
  never the token) on rejection, matching the file's existing notification
  pattern used elsewhere in the same component.
- **Vite dev server**: **not touched**, per the parent decision recorded in
  A01.md. `web/vite.config.ts`, `web/index.html`, `web/package.json`, and
  the lockfile are byte-identical to base (not in the diff above).

## Round 2 — parent review fixes (R1-R4)

Applied in the same two files (`web/src/api/launchAuth.ts`,
`web/src/api/useChatStream.ts`) plus their two test files; no file outside
A02's list was touched. For each fix, the new test was added first and run
against the still-unfixed production code by **temporarily reverting only
that one behavior** with a plain `Edit` (never `git stash`/`checkout`/
`reset`), running the targeted test with `npx vitest run <file> -t
"<pattern>"`, recording the failure, then reapplying the fix via `Edit` and
rerunning the full suite. This was done sequentially, one fix at a time, so
no two reverts were ever live together; each revert/reapply pair is
independently reproducible from this packet's before/after excerpts.

- **R1 — deferred revoke.** `downloadViaAuthorizedFetch`'s `finally` block
  changed from `URL.revokeObjectURL(objectUrl)` (synchronous, right after
  `a.click()`) to `setTimeout(() => URL.revokeObjectURL(objectUrl), 1000)`.
  The anchor is still removed from the DOM immediately; only the revoke is
  deferred, and `finally` still schedules it even if creating/clicking the
  anchor itself throws. **Failing-before**: reverted the `finally` body back
  to the synchronous call, ran `npx vitest run src/api/client.security.test.ts
  -t "R1"` → **1 failed**: `expected "vi.fn()" to not be called at all, but
  actually been called 1 times` (the revoke spy had already fired before
  `vi.advanceTimersByTime(1000)`). Reapplied; full suite green again.
- **R2 — clear 401 message on the SSE chat POST, shared with mount-restore.**
  New `launchAuth.ts` export `nonOkRequestMessage(status, label)`: returns
  `'Not authorized (401) — Daemon may have restarted; reload the page.'` for
  401, else `` `${label} failed (${status})` ``. `useChatStream.ts`'s
  `fetchEventSource` call gained a custom `async onopen(response)` (which
  replaces the library's own `defaultOnOpen`): a non-ok response throws
  `nonOkRequestMessage(response.status, 'Chat request')`; otherwise it
  replicates the library's own content-type check (`EventStreamContentType`,
  now imported from `@microsoft/fetch-event-source`) so a genuinely wrong
  content-type on an *ok* response still throws the library's original
  wording. Mount-restore's 401 branch now dispatches
  `nonOkRequestMessage(401, 'Session restore')` instead of the old
  `'Session restore was not authorized.'` string, so both surfaces read
  identically. **Failing-before (SSE)**: reverted `onopen` out entirely, ran
  `npx vitest run src/api/useChatStream.test.ts -t "R2"` → **1 failed**:
  `expected null to contain "401"` (`result.current.error` stayed `null` —
  nothing surfaced the 401 at all without the handler, since the mocked
  `fetchEventSource` implementation only invokes `init.onopen`, which was
  `undefined`). **Failing-before (mount-restore wording)**: reverted just
  that one dispatched string back to the old text, ran `-t "missing meta
  tag"` → **1 failed**: `expected 'Session restore was not authorized.' to
  contain '401'`. Both reapplied; full suite green again.
- **R3 — chokepoint scoped to same-origin `/api/` paths.** New `launchAuth.ts`
  export `assertApiPath(path: string)`: resolves `new URL(path,
  window.location.origin)` and throws a token-free `Error` unless
  `resolved.origin === window.location.origin` **and**
  `resolved.pathname.startsWith('/api/')` — called at the top of
  `authorizedFetch` (whose `input` parameter is now narrowed from
  `RequestInfo | URL` to `string`, matching every real caller) and,
  separately, in `useChatStream.ts`'s `send()` right before
  `fetchEventSource('/api/chat', ...)`. `new URL()`'s own dot-segment
  normalization means `/api/../x` resolves to pathname `/x` and is rejected
  by the same `startsWith('/api/')` check — no separate traversal logic
  needed. **Failing-before**: reverted `authorizedFetch` to call plain
  `fetch` without `assertApiPath`, ran `npx vitest run
  src/api/client.security.test.ts -t "R3"` → **4 failed** (one per case:
  `https://evil.example/api/x`, `//evil.example/api/x`, `/other`,
  `/api/../x`), each `promise resolved "{ ok: true, status: 200, ...}"
  instead of rejecting` — the control case (`/api/session`) passed in the
  same run, confirming the revert didn't break the ordinary path. Reapplied;
  full suite green again.
- **R4 — per-function enumeration attribution.** The old "attaches header,
  for every function" test called every representative function against one
  shared `stubFetch()` and only asserted the aggregate `calls.length >=
  Object.keys(REPRESENTATIVE_ARGS).length` — a function that made zero
  requests could hide behind another that made two. Rewritten to call
  `stubFetch()` fresh **per function** inside the loop and assert
  `calls.length >= 1` for that function specifically, with every assertion
  message now prefixed `api.${name}:` so a failure names the exact function.
  This is a test-strength fix, not a source defect: run standalone
  (`npx vitest run src/api/client.security.test.ts -t "per-function
  attribution"`) against the round-1 source (before R1-R3's reverts/fixes),
  it **passes** (1 passed) — round-1's production code already sent every
  function's request correctly; R4 only closes a blind spot in how the test
  *would* have caught a regression, so there is no "failing-before" defect
  to reproduce here, per the plan's contingency for a test-only fix.

- **Enumeration**: `Object.keys(api)` is compared against a
  `REPRESENTATIVE_ARGS` table covering all 19 functions; the test fails if
  any exported function has no entry (so a newly added `api` function is
  caught, not silently skipped) and fails if the enumeration is empty. No
  function is intentionally skipped.
- **Header on every function, per-function attribution (round 2, R4)**: a
  fresh `stubFetch()` per function in the loop records that function's own
  calls; every function must make at least one `/api/`-prefixed request
  carrying `X-Daemon-Launch-Token` equal to the meta-tag value, with every
  failure message naming the specific function — a function making zero
  requests can no longer hide behind another making two.
- **Upload**: `uploadFiles` sends a `FormData` body (asserted via
  `instanceof FormData`), the header is present, and `Content-Type` is
  absent (browser sets the multipart boundary itself).
- **Download**: header present on the fetch; `URL.createObjectURL` called
  once; the temporary anchor's `click()` is called exactly once (spied, not
  really navigated — jsdom has no `URL.createObjectURL`, stubbed in
  `beforeEach`); no `a[download]` element is left in the DOM afterward. A
  separate assertion (merged into the token-leak test below) proves a
  download failure rejects without the token in the message. **Round 2
  (R1)**: `revokeObjectURL` is asserted NOT called immediately after the
  awaited call resolves, then called exactly once after
  `vi.advanceTimersByTime(1000)` — proving the revoke is deferred, not
  synchronous.
- **Missing meta tag**: no token header is sent on any call, and
  `api.getSession()` / `api.getModels()` reject on a 401 rather than
  resolving with empty/silent data — checked at both the `client.ts` layer
  (`client.security.test.ts`) and the hook layer (`useChatStream.test.ts`'s

- **Chokepoint scope (round 2, R3)**: `authorizedFetch` rejects

  (`/api/session`) is allowed through.
- **Token never in an error message**: both the generic `json()`-throwing
  path (`getSettings`) and the download-specific path
  (`downloadPromptExport`) are driven through a 500 and their thrown

- **DebugPage check**: a Vite `?raw` import of `DebugPage.tsx`'s source
  (no `@types/node`/tsconfig change needed) asserts `promptExportUrl` and

  the lightweight "check that DebugPage uses it" alternative the frozen

- **SSE** (`useChatStream.test.ts`, `@microsoft/fetch-event-source` mocked
