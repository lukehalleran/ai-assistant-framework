## Contract implemented

1. `TimezoneResolver.get_timezone() -> Optional[str]` and
   `get_user_timezone() -> Optional[str]`: env override -> profile ->
   system `/etc/localtime` -> `None`. `_FALLBACK_TIMEZONE` ("America/Chicago")
   removed entirely. Module and function docstrings rewritten (BC-71) to
   document the `None` contract and that Windows resolves to `None` here
   until A03b-2. Aliases (`central`/`eastern`/... -> IANA) are unchanged.
2. New `utils.timezone_resolver.resolve_event_timezone(explicit=None) ->
   Optional[str]`: an explicit, valid IANA zone wins outright (even when
   the resolver itself is `None`); otherwise falls through to
   `get_user_timezone()`. Shared by all three consumers below so the
   "explicit wins, else resolver, else unknown" rule lives in one place.
3. `core/actions/google_calendar_create.py`: new `timezone_refusal(events)`
   and `UNKNOWN_TIMEZONE_MESSAGE` constant. `create_calendar_event` calls
   it immediately after `_event_items` validation and BEFORE the
   duplicate-check GET or any create POST — a TIMED event with no
   resolvable zone refuses the WHOLE proposal (no partial writes) with
   `ActionResult(success=False, message=UNKNOWN_TIMEZONE_MESSAGE)`.
   `_event_body` now calls `resolve_event_timezone` instead of `... or
   get_user_timezone()`. All-day events are unaffected (never consult the
   zone at all).
4. `core/actions/google_calendar_modify.py`: `update_calendar_event`'s
   timed-event branch calls `resolve_event_timezone` and refuses (same
   message, same shape) before `_resolve_event`'s GET or the PATCH.
5. `core/actions/registry.py`: new `calendar_timezone_unknown(params) ->
   bool`, placed beside `calendar_datetime_shape_errors` and mirroring its
   exemption shape (a no-op for all-day events and for any payload with no
   `start_time`/`end_time`, i.e. non-calendar actions). Wired into
   `resolve_forced_action`'s calendar branch immediately after the
   `_shape_bad` check, so a forced retry asks for the timezone before a
   card is minted. `_current_wall_clock()` now branches explicitly on
   `get_user_timezone() is None` (naive `datetime.now()`, documented) —
   the ZoneInfo `try/except` is now for the belt-and-suspenders case only,
   never the primary path for "unknown," per the plan's "not
   exception-driven" instruction.
6. No new config keys, no prompt changes, nothing outside these files.

## Contract for A03b-2 (Windows OS timezone resolution)

A03b-2 plugs a Windows registry lookup into the SAME `Optional[str]`
contract this batch established:

- `TimezoneResolver.get_timezone()` / `get_user_timezone()` must keep
  returning `Optional[str]` — A03b-2 adds a fourth tier (after system
  `/etc/localtime`, before the final `None`) that consults the Windows
  registry (e.g. `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\TimeZoneInformation`)
  and maps its `TimeZoneKeyName` to an IANA zone (a Windows-name ->
  IANA-name table, analogous to the existing US-label `_TIMEZONE_ALIASES`,
  is out of this batch's scope but will need the same
  validate-before-return discipline as `_is_valid_iana_zone`).
- `None` must remain the ONLY "unknown" signal — A03b-2 must not introduce
  a second fallback (e.g. defaulting to UTC when the registry key is
  missing or unparseable). The three consumers this batch fixed
  (`create_calendar_event`, `update_calendar_event`, `_current_wall_clock`,
  plus `resolve_forced_action`'s calendar branch) already treat `None` as
  the refuse-and-ask signal; they need no further changes once A03b-2
  makes Windows resolve correctly when the information is genuinely
  available.
- `resolve_event_timezone(explicit=None)` is the single place "explicit
  wins, else resolver" logic lives; A03b-2 does not need its own version.
- Per the plan's "A platform API is unavailable on Linux" contingency,
  this batch could not exercise a real Windows registry — A03b-2 must
  unit-test with a registry/timezone stub (mirroring how this batch
  mocked `_resolve_system_timezone`) and add a Windows CI/manual evidence
  row; platform acceptance is explicitly pending, not inferred.

  - An unrecognized zone (a typo, or a label outside the alias table) was silently replaced by the user's own zone, so the event would be created at the wrong wall-clock time. Before this batch, Google would have rejected the invalid string loudly.
- **Failing-before**, with the new tests added first:
  - `test_explicit_alias_zone_is_honored_when_resolver_unknown` → failed: refused with `UNKNOWN_TIMEZONE_MESSAGE`.
  - `test_unrecognized_explicit_zone_refuses_instead_of_using_user_zone` → failed: `get` was awaited once, meaning it proceeded with Denver.
- **Fix (`utils/timezone_resolver.py`).** A non-empty explicit zone resolves through `TimezoneResolver._resolve_tz_value` (IANA or alias), and an unrecognized one returns `None` (refuse and ask). Only an absent explicit zone falls through to the user's zone. `calendar_timezone_unknown` and both executors inherit the behavior because they share this function.
