## 2. Requirement/defect ID and invariant

- BC-21 (compare/coerce on the serialized form) sibling of F03/A04's
  `core/grounding_check.py::_parse_verdict` and S01's
  `utils/web_search_trigger.py::LLMSearchTriggerResponse.parse`.
- Invariant (parent contract): the top level must be a JSON object;
  `passes` (bool) and `confidence` (finite non-bool number in [0,1]) are
  REQUIRED — no default-to-pass, absent or wrong-typed rejects the whole
  payload; `issues` (list of str) and `suggestion` (str) are OPTIONAL —
  absent keeps the documented empty default, present must have the taught
  type or the payload is rejected. Any violation returns `None` with
  exactly one warning naming only the field and its Python type — never the
  model's own issues/suggestion text.
- Why the source seam owns the fix: `ResponsePlanner._parse_review` is the
  single place that turns the review-gate LLM's raw JSON text into a
  `ReviewResult`; it called `bool()`/`float()` directly on untrusted model
  output, so a JSON payload that simply omitted `passes` (which the prompt
  never tells the model is optional — see §3) silently became
  `passes=True` — a malformed or incomplete review recorded and read
  downstream exactly like a genuine pass (`bool(None-key.get("passes",
  True))` fail-open).

## 3. Required vs. optional fields (file:line evidence)

The review prompt (`core/response_planner.py:654-659`, `review_answer`)
teaches all four fields unconditionally, with no "(optional)" annotation on
any of them:
```
'- "passes": true if the response adequately addresses the plan, false otherwise\n'
'- "confidence": 0.0 to 1.0 (how confident you are in this judgment)\n'
'- "issues": list of strings (specific problems, empty if passes)\n'
'- "suggestion": string (how to improve, empty if passes)\n\n'
```
Since the prompt text alone doesn't separate required from optional, the
decisive test (matching S01's own two-tier reasoning: "only fields
load-bearing for this module's own routing logic are required") is what the
ONLY caller, the log-only review gate in `gui/handlers.py`, actually reads
from the returned `ReviewResult`. A full grep of `_review\.` in
`gui/handlers.py` finds exactly these seven reads, all in one block
(`gui/handlers.py:4655-4672`):
```
4655: "review_passed": bool(_review.passes),
4656: "review_confidence": round(float(_review.confidence), 3),
4660: and not _review.passes
4661: and _review.confidence >= RESPONSE_REVIEW_CONFIDENCE_THRESHOLD
4665: f"(confidence={_review.confidence:.2f}, "
4666: f"issues={_review.issues}). Log-only — "
4672: f"(confidence={_review.confidence:.2f})"
```
`.passes` and `.confidence` gate the pass/fail branch AND are recorded
verbatim into turn telemetry (`review_passed`, `review_confidence`) — both
load-bearing, so both are REQUIRED. `.issues` is read only inside the
warning log message (display-only, never branching). `.suggestion` is
**never read by the caller at all** — grep confirms zero occurrences of
`_review.suggestion` anywhere outside `core/response_planner.py` itself.
Both stay OPTIONAL.

- `config/app_config.py` has no review-gate mode key at all — grepping

  config toggle between "log-only" and "enforcing" — unlike
  `GROUNDING_MODE`, the review gate's log-only behavior is hardcoded in
  `gui/handlers.py`, not config-driven.
- `core/orchestrator.py` never calls `review_answer` or reads
  `ReviewResult` at all (grepped: zero matches). It only constructs the
  `ResponsePlanner` (`core/orchestrator.py:644-655`,
  `self.response_planner = ResponsePlanner(model_manager=model_manager)`)
  and drives the PRE-answer `create_plan()` call
  (`core/orchestrator.py:1656-1678`), setting
  `self._current_response_plan`. Review is entirely a `gui/handlers.py`
  concern.
- `gui/handlers.py:4628-4637` carries the mode declaration in-line, dated
  2026-08-28: *"Post-Answer Review Gate: LOG-ONLY... The gate previously
  ran a silent agentic retry and SWAPPED the response before storage when
  review failed at high confidence. An 8-week telemetry audit showed
  exactly ONE real-turn swap ever... Stored must always equal seen: the
  review still runs and records pass/fail/confidence telemetry for
  recalibration, but NEVER replaces the response."* This matches BC-45 (the
  incident list's own 2026-08-28 entry: "review gate's only production
  'fix' was a silent swap (→ log-only)") and CM-04 (`GROUNDING_MODE=log_only`
  cited as the doctrine's exemplar; the review gate is its own independent
  instance of CM-04, applied via code, not config).
- The actual gate logic (`gui/handlers.py:4639-4680`): `review_answer()` is
  called; if it returns a `ReviewResult` (`_review is not None`), telemetry
  is recorded (line 4653-4657) and, only if `not _review.passes and
  _review.confidence >= RESPONSE_REVIEW_CONFIDENCE_THRESHOLD`, one
  `logger.warning` fires (line 4663-4668) — in every case the response
  itself is never swapped (no code path replaces `final_output`/
  `display_output` from a review verdict anywhere in this block).
- **What `None` does today (before this batch, and unchanged after it):**
  neither the `ctx.telemetry.update(...)` block (guarded by `if _review is
  not None:`) nor the warning/debug branch (guarded by `if (_review and
  ...)` / `elif _review:`) executes. A `None` review is therefore already
  "review unavailable" in the caller's existing code — nothing is recorded,
  nothing is acted on, as either a pass or a fail. This was already true
  for the pre-existing failure modes (timeout, provider exception,
  unparseable JSON); this batch's fix only widens which malformed payloads
  reach `None` instead of silently becoming a fabricated `ReviewResult`
  (see §7's failing-before proof for `passes` specifically). No caller
  change was needed, and no receipt/schema exists for "review unavailable"
  to be recorded into — consistent with the routine-failure contingency
  ("Verifier JSON is malformed or wrong-typed → treat as abstain/invalid;
  leave response unchanged only in log-only mode") and requiring no
  escalation.

## 6. Fix implemented (`core/response_planner.py`)

Added `import math`. Added one module-level constant,
`_REQUIRED_REVIEW_FIELDS = ("passes", "confidence")`, and one new private
helper, `_invalid_review_reason(data: dict) -> Optional[str]`, placed
immediately after the `ReviewResult` class it validates. It returns `None`
when `data` satisfies the strict contract, else the first failing field
name plus its received Python type name — never the field's own value
(privacy: `issues`/`suggestion` may quote response-critique text).

`_parse_review` (`core/response_planner.py`, staticmethod) now: parses JSON
inside the existing try/except (unchanged
`except (json.JSONDecodeError, ValueError, TypeError)` → `logger.debug` →
`None`); rejects a non-`dict` top level with one `logger.warning` naming
the received type (fixes an uncaught `AttributeError` — see §7); calls
`_invalid_review_reason` and returns `None` with one `logger.warning` on
any violation; and only once validation passes, constructs
`ReviewResult(passes=data["passes"], confidence=float(data["confidence"]),
issues=data.get("issues", []), suggestion=data.get("suggestion", ""))` —
`passes`/`confidence` are read directly from already-type-checked keys (no
`bool()`/coercive `float()` call on untrusted input remains; the
`float(...)` here is now an identity/widening cast on a value already
proven to be a finite non-bool int/float in [0,1]).

Not changed: `ReviewResult`'s public fields/defaults/Pydantic constraints,
`ResponsePlan`, `_parse_plan`, `should_plan`, `create_plan`,
`format_plan_injection`, any `unsupported_key_points`/embellishment-guard
logic, `core/orchestrator.py`, or `gui/handlers.py`. No schema/receipt
change was needed, so no escalation packet applies.
