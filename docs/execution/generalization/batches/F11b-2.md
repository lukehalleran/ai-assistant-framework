## Considered and NOT used

Per CONTRACT item 1: the store's `update_metadata(collection_name, doc_id, metadata_updates) -> bool` (a metadata-merge update, already used unchanged by `update_tracking_metadata`) was considered as an alternative to the staged write-then-delete replacement for `update_status`, and rejected:
- It swallows its own errors to a bare `False` (`except Exception as e: logger.error(...); return False`) rather than raising a typed error the caller can distinguish from "not found" — the staged replacement instead gets a typed `StoreWriteError` from `store_proposal()` for the write step, which is exactly what the contract requires catching.
- A merge only touches the keys explicitly passed in `metadata_updates`. `update_status` must apply whichever fields `mark_approved()` / `mark_rejected()` / `mark_completed()` / `mark_failed()` changed (status, rejection_reason, commit_hash, executed_at, rollback_available, modified_at, depending on the transition) — a merge call would have to enumerate exactly that set and would silently keep stale values for any field it omitted, including any field added to `CodeProposal.to_metadata()` in the future. Re-storing the full proposal via `store_proposal(proposal)` regenerates the complete, current metadata dict from `to_metadata()` every time, so there is no such staleness class.
