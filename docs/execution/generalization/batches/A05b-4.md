## 6. Finding: the agentic route's post-review teardown does not dispatch storage (pre-existing, out of scope)

While writing the teardown-regression test (mirroring A05b-3's D1 test),
discovered that a `GeneratorExit` delivered at the agentic route's
suspended `yield _final_chunk` — via `_buffer_grounding_draft`'s own
`finally: await chunks.aclose()`, itself triggered by the event loop's
async-generator finalizer once nothing else references the suspended
wrapper generator — propagates straight out of `_run_agentic_search`
without resuming the sequential code after the yield (lines ~4071–4128:
sanitization, the parity guard, `_dispatch_storage`, `_write_turn_telemetry`,
`ctx.handled = True`). This is standard Python generator-close semantics
(throwing `GeneratorExit`/calling `aclose()` on a suspended generator
raises at the yield point; it does not resume execution past it) and is
**unrelated to this batch's edit** — reproduced identically pre- and
post-fix (`test_agentic_teardown_after_reviewed_final_chunk_writes_no_cancel_receipt`
asserts `turn_setup.storage.assert_not_called()` and passes both before and
after §5's edit).

This differs from the enhanced route, where A05b-3 already moved the
storage dispatch into a `finally:` block specifically so it survives this
exact teardown path (its own D1 test,
`test_teardown_after_reviewed_final_chunk_still_stores`, asserts storage
WAS called). The agentic route has no such `finally:` around its storage
dispatch, and OWNERSHIP for this batch restricts edits to exactly 3
shapes (the reviewed-delivery flag, the `except BaseException` clause, and
the receipt write) — restructuring the storage-dispatch sequencing itself
is out of scope here.

Net effect for the CONTRACT line "A teardown AFTER the agentic reviewed
final chunk: storage and telemetry proceed as today, with no
`cancelled_before_review`": today, "storage... proceed[ing]" does not
literally hold for this narrow post-yield-before-further-consumption race
(storage silently does not fire); what this batch's fix DOES guarantee,
and what actually matters for the D2 contract, is that no
`cancelled_before_review` receipt is spuriously written in this scenario
either (`review_delivered` was already `True`) — verified. Flagging this
storage-on-teardown gap as an open finding for the parent / a future batch,
analogous to A05b-3 §11 flagging the agentic route's cancel-during-review
behavior as unexamined at the time.

## 11. Exact receipt semantics per exit path (agentic route)

- **Correct mode, cancel/BaseException BEFORE the reviewed final chunk:**
  the new `except BaseException` clause sets `_base_exc_active = True` and
  re-raises unchanged; `finally:` sees `_correct_mode and _base_exc_active
  and not review_delivered` → writes exactly one receipt
  (`ctx.telemetry["delivery"] = "cancelled_before_review"`,
  `_write_turn_telemetry(..., 0, response_text="")`) then the exception
  continues propagating (the `finally:` never swallows it). No assistant
  text is stored (the sequential storage-dispatch code, earlier in program
  order than the point of cancellation, never runs — already true before
  this batch).
- **Teardown AFTER the reviewed final chunk (`review_delivered` True):**
  the `except BaseException`/`finally:` gate still runs (a `GeneratorExit`
  at that later yield also hits it) but writes nothing
  (`not review_delivered` is False). Storage/telemetry are unaffected by
  this batch either way — see §6's finding for what "unaffected" concretely
  means today.
- **Internal `except Exception`** (existing, unedited clause): falls
  through to enhanced as before; `_base_exc_active` stays False, so the
  `finally:` gate never fires — no agentic receipt; the enhanced route
  (already fixed by A05b-3) owns the turn's one delivery.
- **log_only / off:** `_correct_mode` is False in the `finally:` condition
  in both cases — byte-identical to pre-A05b-4 behavior, including under
  cancellation (`test_log_only_agentic_cancel_keeps_storage_call`).

**Double receipt:** proven impossible by construction and by test. A
BaseException that reaches the new `except BaseException` clause is
re-raised unchanged and propagates straight out of `_handle_submit_inner`'s
`async for _c in _agentic_stream: yield _c` (line ~5644) — it is NOT caught
there, so control never reaches the `_run_enhanced` dispatch a few lines
below (which only runs when the agentic `async for` loop completes
normally and `ctx.handled` is still False). `test_agentic_cancel_before_review_gate_and_receipt`
asserts exactly one row. For the Exception-fallback path (not a
cancellation), `test_agentic_exception_fallback_writes_no_agentic_receipt`
asserts exactly one row (enhanced's), with no `delivery` key — proving the
two routes' receipts never both fire for one turn.
