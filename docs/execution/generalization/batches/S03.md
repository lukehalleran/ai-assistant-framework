## 2. Requirement/defect ID and invariant

- BC-21 (compare/coerce on the serialized form) sibling of F03/A04's
  `core/grounding_check.py::_parse_verdict`, S01's
  `utils/web_search_trigger.py::LLMSearchTriggerResponse.parse`, and S02's
  `core/response_planner.py::ResponsePlanner._parse_review`.
- Invariant (parent contract): every field `_parse_proposal` reads from the
  model's raw JSON — `requires_tests`, `priority`, `tags`, `affected_files`,
  `estimated_complexity` — is OPTIONAL: absent keeps its documented default,
  but a PRESENT field must have its taught type, or the whole proposal is
  rejected (`None`) with exactly one warning naming only the field and its
  Python type. Unlike S01/S02 there is no REQUIRED field and no top-level
  "must be a JSON object" case: `_parse_proposal(self, data: dict)` already
  only ever receives a `dict` from its sole caller, `_parse_response`, which
  filters to dict items on every parse path (JSON array, single object, or
  line-delimited); a non-dict argument, if it ever occurred, already hits
  the pre-existing broad `except Exception` (unlike S01/S02's narrower
  `except (JSONDecodeError, ValueError, TypeError)`, which is why F03/S01/S02
  had an uncaught-`AttributeError` defect and S03 does not). `classify_proposal`
  (the supervision/risk classifier) is out of scope — it must never be
  changed, and per this batch's own finding, must never be CALLED with a
  rejected payload's data either.
- Why the source seam owns the fix: `_parse_proposal` is the single place
  that turns one raw proposal dict into a `CodeProposal`. It called `bool()`/
  `int()` directly on untrusted model output (`bool(data.get("requires_tests",
  True))`, `int(data.get("priority", 5))`), so `"requires_tests": "false"`
  silently became Python `True` and `"priority": true` (a JSON bool) silently
  became `1`. Separately, `list(affected_files)` at line 346 — used to build
  `touched_paths` for the risk classifier — silently exploded a string
  `affected_files` into single characters (`list("abcdef") ==
  ['a','b','c','d','e','f']`) and fed them to `classify_proposal` *before*
  the malformed proposal was eventually (and only incidentally) rejected by
  an unrelated Pydantic `ValidationError` when constructing `CodeProposal`.

## 3. Pre-fix behavior probe (read-only, on the unpatched source, before any test was run)

Before writing the test file, the deployed (unedited) `_parse_proposal` was
probed directly (`python -c`, no pytest, no edit) to establish ground truth

- `requires_tests` in **every** form tested (`"false"`, `"true"`, `0`, `1`,
  `None`, `"yes"`) was silently accepted and coerced (`bool()` never raises):
  `requires_tests="false"` produced `CodeProposal(requires_tests=True, ...)`.
  This field had **zero** accidental protection before the fix.
- `priority`: `True`/`False` (bool) silently became `1`; `7.9` (float)
  silently truncated to `7`; `"8"` (str) silently coerced to `8`. `None` and

  pre-existing broad `except Exception`, and already returned `None`.
- `tags`/`affected_files` wrong-typed values (`"abc"`/`"abcdef"`, `123`,
  `None`, `{"a": 1}`, `["ok", 5]`, `[None]`) already returned `None` for
  every case tested — but only by *accident*, via Pydantic's own
  `List[str]` field validation raising when `CodeProposal(...)` was
  constructed (verified directly: `CodeProposal(tags="abcdefghijklmno")`
  raises `pydantic_core.ValidationError: Input should be a valid list`).
  Crucially, for a **string** `affected_files`, `classify_proposal` (the
  risk classifier) was already called, with corrupted `touched_paths`,
  *before* that later Pydantic rejection: a spy on

  `classify_proposal(['a', 'b', 'c', 'd', 'e', 'f'], ...)` for
  `affected_files="abcdef"`.
- `estimated_complexity` wrong-typed values (`5`, `True`, `None`,
  `["low"]`) already returned `None` — via `AttributeError` on `.lower()`,
  caught by the broad except, and (per the probe) this happens *before*
  `classify_proposal` is reached, so this one field was already isolating
  the classifier correctly, purely by accident of code order.

This probe directly shaped which test cases are genuine failing-before

## 6. Fix implemented (`knowledge/proposal_generator.py`)

No new import was needed (`Optional` was already imported). Added one
module-level tuple, `_PROPOSAL_STR_LIST_FIELDS = ("tags", "affected_files")`,
and one new private helper, `_invalid_proposal_reason(data: dict) ->
Optional[str]`, placed between the module logger and the
`GoalDirectedGenerator` class. It returns `None` when `data` satisfies the
strict contract, else the first failing field name plus its received Python
type name — never the field's own value (privacy: title/description/tags
may quote model-authored or user-derived text).

`_parse_proposal` now calls `_invalid_proposal_reason(data)` as the very
first statement inside its existing `try:` block — before the title check,
before `estimated_complexity`'s `.lower()` call, before `affected_files` is
read, before `touched_paths` is built, and before `classify_proposal` is
called. On a violation it logs one `logger.warning(f"[ProposalGenerator]
Rejected proposal JSON: {reason}")` and returns `None`, matching the
existing `[ProposalGenerator]` log-tag convention already used elsewhere in
this file. Every existing coercion line downstream
(`bool(data.get("requires_tests", True))`, `int(data.get("priority", 5))`,
`data.get("tags", [])[:10]`, `.lower()` on `estimated_complexity`,
`list(affected_files)` for `touched_paths`) is **unchanged** — since every
field in this contract is OPTIONAL (unlike S01/S02's REQUIRED fields, which
switched to direct `data["field"]` access), `data.get(field, default)` is
already the correct idiom, and once the validator has run, these become
pure identity operations on a value already proven to be the taught type
(or the untouched default) — not coercions of untrusted input. This is a
purely additive patch: `git diff --numstat` shows `52 insertions, 0
deletions`.

Not changed: `classify_proposal`/`requires_human_ack`
(`memory/proposal_risk.py`, read but not touched — out of scope per the
brief), `CodeProposal`/`ImplementationStep` (`memory/code_proposal.py`),
`_parse_response`, `_build_prompt`, `gather_context`, `_annotate_conflicts`,
`generate_code_for_proposal`, either production caller, or any other file.
