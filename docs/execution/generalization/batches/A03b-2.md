   plain dict literal with 139 entries sorted by Windows key name, generated

   version, generation date, exact command). No runtime babel import, no
   hand edits.

   - New private helper `_resolve_windows_registry_timezone() -> Optional[str]`:
     imports `winreg` lazily (inside the function — it does not exist off
     Windows, so the module never imports it unconditionally), reads HKLM
     `SYSTEM\CurrentControlSet\Control\TimeZoneInformation` value
     `TimeZoneKeyName`, looks it up in `WINDOWS_TO_IANA`, and returns the
     mapped zone only if `_is_valid_iana_zone` accepts it. Any exception
     (unknown key via `.get` returning `None`, `OSError` from the registry
     read, or a validation failure) returns `None`. The debug log carries
     only the registry key name, never any other registry value.
   - `_resolve_system_timezone()` now branches on `sys.platform == "win32"`
     first, delegating to the new helper; the non-Windows body (the
     `/etc/localtime` parse) is byte-identical to before.
   - Module docstring (resolution-order items 3-4) and the function's own
     docstring rewritten to describe the Windows branch and its `None`
     cases (BC-71) instead of deferring to "a separate later batch (A03b-2)".
   - Two new top-level imports needed to support the above: `import sys`
     (for the platform check) and `from utils.windows_timezones import
     WINDOWS_TO_IANA`. `winreg` itself stays a lazy, function-local import.

  ship tzdata (`daemon.spec` has no tzdata entry, and `daemon.spec` is
  read-only for this batch), so `zoneinfo` on a packaged Windows build may
  have no tzdata available. Without tzdata, `_is_valid_iana_zone` rejects
  every mapped value and `_resolve_windows_registry_timezone` correctly
  returns `None` — the same safe "unknown, ask the user" behavior as any
  other unmapped case, never a crash or a wrong guess. This batch does NOT
  change `daemon.spec` or otherwise address the packaging gap; a future
  batch owning `daemon.spec` should add the tzdata data-file entry so a
  packaged Windows build can actually resolve a zone rather than always
  landing on the safe-but-unhelpful `None`.
- This batch could not exercise a real Windows registry (Linux sandbox, per
  the plan's "A platform API is unavailable on Linux" contingency); the unit
