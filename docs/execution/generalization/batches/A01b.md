## 2026-09-14 — SECURITY NOTE

- **Trust-boundary change**: before this batch, only a loopback caller could
  ever receive the launch token via `GET /` or pass the Host check at all.
  After this batch, a caller whose Host header exactly matches the
  owner-configured `api.host` (when it is a specific, non-wildcard address)
  or an entry in `api.allowed_hosts` is treated identically to a loopback
  caller — it receives the token from `GET /` and can call every `/api/*`
  route with it. The new trust boundary is therefore **whoever can reach
  the bound socket and present that exact Host header** — for the owner's
  stated use (a Tailscale-bound `api.host`), that is the owner's tailnet ACL,
  not this server. This is an intentional, owner-approved widening, not a
  bug: it only ever trusts hosts the owner explicitly configured.
- **DNS-rebinding analysis**: `normalize_trusted_hostnames`/`is_allowed_host`
  do exact-string-match only (a normalized IP literal or a normalized
  hostname), never a suffix, wildcard, or pattern match (proved by
  `test_no_suffix_or_pattern_match`: `100.64.0.10.evil.example` and
  `evil.example` are both rejected against a trusted set containing only
  `100.64.0.10`). A classic DNS-rebinding attack (a hostile page's DNS name
  later resolves to a loopback/internal IP) still cannot pass the Host
  check here, because the check is on the **Host header string** the
  browser sends — same-origin fetches from a trusted page send that exact
  trusted hostname as Host, but a rebound attacker-controlled hostname
  (e.g. `attacker.example`, even once it resolves to `100.64.0.10`) still
  sends `Host: attacker.example`, which is not in `LOOPBACK_HOSTNAMES |
  trusted_hostnames` and is rejected. The remaining exposure is unchanged in
  kind from A01: whoever can make a browser send a request with the exact
  trusted Host string (i.e., whoever the owner's network already lets reach
  that address under that name) is trusted — this batch does not add a new
  rebinding vector, it only adds more exact strings to the existing
  allowlist mechanism A01 already established for loopback names.
- **HTTP-over-tailnet transport assumption**: this batch does not add HTTPS
  or any `tailscale serve`/TLS-terminating-proxy support — the launch token
  and all traffic to a trusted non-loopback host are still carried over
  plain HTTP, same as A01's loopback traffic. On a Tailscale network this is
  the owner's existing accepted risk model (WireGuard already encrypts the
  tailnet hop), but it is recorded here as an explicit limitation, not
  silently assumed: this batch neither improves nor worsens that transport
  assumption, it only extends the Host allowlist that gates who may use it.
- **G06-A04** (non-loopback listener/bind review) remains **open**, as in
  A01 — `main.py`'s `uvicorn.run(app, host=API_HOST, port=API_PORT)` bind is
  unowned by both A01 and A01b. This batch is an **owner-approved
  exception** to treating a non-loopback bind as an unreviewed risk: the
  owner has already decided (relayed decision, top of this packet) to bind
  non-loopback for Tailscale access, so A01b makes the *authorization*
  contract accept that reality rather than silently 400-ing every request
  the owner's own topology sends. It does not itself review or approve the
  bind/listener configuration.
- **A01's "must not land or deploy without A02" still holds**: the built SPA
  still sends no launch token without A02's client transport; this batch
  changes only which Host values the server-side check accepts, not the
  token-delivery contract A02 depends on.
