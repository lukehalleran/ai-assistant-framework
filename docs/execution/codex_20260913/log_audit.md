There are 54 `Semantic search timeout after 1.5s` warnings across the sampled logs (53 in the first, 1 in the second); an example is `daemon_debug_20260913_165017.log:746`. The turn record has no per-task success/timeout status, so a duration alone cannot distinguish a completed retrieval from a timed-out one. This is evidence of repeated timeout behavior, not evidence that a particular answer was wrong or that the fallback failed.

On the 87 records with wall time, median was 21.1 s, p90 42.45 s (linear interpolation, confirmed by the offline rollup), maximum 138.7 s. The maximum record (`logs/turn_records.jsonl:2755`) spent 128.8 s in the agentic loop after a 9.7 s preparation phase; it recorded three rounds without a timeout flag. The late 19:54 record (`:2762`) took 44.0 s total, of which prepare was 29.6 s and prompt build 25.3 s. Its concurrent task timings included 23.6 s for memories, 21.6 s for summaries, and 20.5 s for semantic retrieval. These are observed timings, not proof of a defect; they show where an offline rollup should direct review.

**Class mapping:** BC-72 for missing per-task outcome receipts; BC-47 (failure/not-run collapsed into valid empty) is a hypothesis until a caller is shown to consume timed-out retrieval as an ordinary empty result. BC-41 (eager expensive acquisition) is a lower-confidence candidate for the slow preparation/context path. The 138.7 s maximum is agentic-loop time, so it should not be misattributed to context acquisition.

## Highest-value safe follow-up plan for a cheaper worker

1. **Build a read-only offline rollup first.** Add one isolated parser/report script and synthetic fixture tests, with no runtime imports and no access to `data/`. Accept only explicit input paths and a local-date filter. Stream JSONL and debug logs, convert timezone-aware timestamps to CDT, and report counts, timing percentiles, warning/error categories, optional-field coverage, and action-state transition counts. Do not print query/response text, retrieved context, names, tool parameters, URLs, IDs, or log previews. Test date boundaries, UTC-to-CDT conversion, sparse optional fields, malformed rows, stable count summaries, and redaction. Its output should contain no message-level material.
2. **Keep action-result context as a separate behavior batch.** After Plan 2 freezes action/history ownership, add a trusted, compact prior-turn action receipt for pending/approved/executed-success/executed-failure states. Source it from the action result ledger, include only the minimum user-relevant status, and never infer success from generated prose or expose raw parameters. Test a later “did that happen?” turn against each lifecycle state and assert that no receipt is shown before the corresponding state transition. Keep this out of the offline rollup and coordinate any shared `gui/handlers.py`, chat-service, or orchestration seam with the Plan 2 owner.
3. **Add timeout state only through the reserved telemetry owner.** Plan 2’s A07 owns `utils/turn_telemetry.py` and later sole-owner integration in `core/orchestrator.py`; do not independently wire turn telemetry in another batch. Ask that owner to distinguish attempted/succeeded/timed-out/skipped for retrieval tasks in the fixed allowlist, with no query or retrieved content. A focused synthetic test should prove timeout and skipped are not serialized as success or empty-result success.
4. **Defer low-confidence cleanup.** Inspect why image-empty paths are logged at WARNING and whether the People API denial is expected configuration before changing severity or fallback behavior. Preserve explicit provider-credit errors as operational events.
