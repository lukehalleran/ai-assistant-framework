## Observed shape and semantic risk

Each listed gatherer wraps its store/provider read in `except Exception` and returns [] or '' — exactly what a genuinely empty section returns. The formatter then omits the section and the model can state that no notes, uploads, events or facts exist when the read failed (probe backlog Q12; BC-47). The turn receipt cannot tell the two apart.

This is a bounded structural review, not a reproduced runtime failure. If
the source owner shows a site is not an instance of the class, the response
should say so with deployed-function evidence. The class-guard owner then
decides between a detector change and continued accepted debt.

## Requested remedy (the source owner owns the design)

Carry a failure outcome out of the gatherer layer (CM-05 tri-state: a receipt or source field per section distinguishing failed/unavailable from empty) and let the formatter or prompt state 'could not check' where a section failed. The design is the source owner's; the requirement is that a failed read never renders identically to an empty store.

## Expected deployed-function regression tests

For the gatherer entry points, inject a raising store/manager through the deployed gatherer and assert the outcome/receipt is marked failed (not empty) and the rendered prompt does not present an empty section as 'none'; paired control with a genuinely empty store stays empty.
